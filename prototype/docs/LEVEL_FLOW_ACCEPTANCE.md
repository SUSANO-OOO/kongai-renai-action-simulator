# 11ステージの面白さ・1体開始・100体ゴールの受入契約

## A. 固定の状態遷移

- ラン開始: `troopCount = 1n`（モード/ステージ/装備/ユーザーレベルに関係なし）。ラン中のみ掛け算/増員で変化。
- 途中で`troopCount = 0n`になればその場で敗北。ゴール時は `>= 100n` ならクリア、`1n..99n`なら到達失敗。
- クリア報酬（XP/コイン/称号/次面解放）は**成功時のみ**。失敗した場合に全報酬・勝利演出を発火しない。
- ローカルセーブ破損、リトライ、難易度切替、戻る/再開で開始人数や勝敗が混ざらない。
- 外見のスキン、15称号、ユーザーレベル、購入履歴はゲームの戦力数/攻撃力/速度/難度計算へ入力しない。

## B. 各レベルの設計カード

各面・各モードに、最低以下の項目を手作りデータとして登録する。

1. 独自のテーマ/背景モデル/キャラクター/色と音のモチーフ。
2. 新しい敵行動あるいは障害ギミック、他面と異なる山場。
3. ゲートの組合せとその意図：増員ルートと安全・強化ルートのトレードオフ。
4. 1体から始まって100体到達可能な**実際のゲーム操作**の攻略例（選択したゲート・敵回避と残数推移）。
5. NORMALとHARDの差分スクリプト（HARDは敵体力だけ上げた複製不可）。
6. 走行時間の実測、最初の報酬までの時間、最大の空走区間、予告可能な反応時間。
7. 0体/99体/100体/1000体の勝敗と結果UI、コイン/XP/称号の重複付与防止。

## C. 最初に作るQAの自動化

- 10面の`stage.id`とイベントの位置/レーン/種別/順序を検査。
- 全面が1体スタートで、成功閾値が100体である設定値と試作コードを検査。
- 抽象的なルート探索（倍率と障害/敵の代表損失）を実行し、NORMAL/HARDでゴール100体に達する経路が存在するか予備検査。**予備検査は実機勝利証明の代用ではない**。
- HARD専用データがまだ存在しない現状は、テスト合格にしない。「未実装のまま承認不可」と分類。
- モデルやUIの実素材が未作成なら `approvedForProduction=false` を維持。実ファイルの存在/見た目/音/肖像権は自動検査だけでは完結しない。

## D. 実機プレイ検証（素材査定の後）

- 代表端末：iOS Safari / Android Chrome、360/390/430px幅、低/標準/高画質、30/60FPS設定。
- 各モード10面をプレイ記録。成功、0体負け、ゴール100未満、再戦、戻る、スキン装備、称号選択、保存復帰まで実施。
- フリーレーン：左右に連続移動、指を離しても横位置維持、境界外に出ない、ゲート/敵/障害の当たり判定が映像と一致。
- 一定の勝率を保証したと言わず、複数名に初見テストして詰まったイベントと理由を記録。勝利した人の動画をコース攻略例として提出。
- 1万体、10万体、巨大な有限BigIntで画面/UI/戦闘/保存が壊れないかを測定。表示は端末負荷に合わせてインスタンスの数を制御。
- すべて修正した後、３回の「ゲーム性→画面音→実機性能」監査と、変更箇所の回帰確認を行う。
